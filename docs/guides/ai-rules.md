# AI 执行规约

本文参考 Nexus 仓库规约整理，是 BeiDou Server 仓库的 AI / 自动编码统一规则。

## 阅读顺序

接手非平凡任务时，最低阅读顺序如下：

1. `AGENTS.md`
2. `docs/README.md`
3. `docs/guides/coding-style.md`
4. 任务相关设计文档，例如 `docs/life-proof-quest-chain.md`、`docs/interaction-hook-v3.md`
5. 涉及打包、SQL、WZ、脚本、客户端补丁时，继续阅读 `AGENTS.md` 中对应规范

## 致命规则

- **打包补丁前必须 `mvn clean package -pl gms-server -DskipTests`**。`mvn compile` 只编译
  `.class`，不更新 `target/BeiDou.jar`。Patcher 的 `build.ps1` 从工作目录复制 JAR，如果 JAR
  是旧的，所有 Java 改动静默丢失。修改任何 Java 代码后，重新打包前必须先 `mvn clean package`。

## 总原则

1. 文档、协议、状态机、SQL、代码、测试必须同向落地。
2. 发现设计和代码不一致时，先收敛不一致，再继续新增能力。
3. 如果旧方案可以完全替换，不保留中间态配置、兼容分支、旧接口或临时模式。
4. 修改涉及客户端、服务端、WZ、脚本、SQL 或补丁包时，必须说明跨仓库影响。
5. 与用户交流、交付总结和普通文档描述默认使用中文；命令、路径、API、协议名、配置 key、日志字段保留原文。

## 防御性编码

1. 函数入口先处理 `null`、空值、非法枚举、越界参数、缺失配置和依赖错误。
2. 所有前置条件通过后，再进入主逻辑。
3. 依赖调用返回错误时先处理错误，再继续后续逻辑。
4. 不把 happy path 包在大块 `if ok { ... }` 中，再在函数末尾补错误。
5. 分支已经 `return`、`continue` 或 `break` 后，不再用不必要的 `else` 包住后续逻辑。
6. 触达旧代码时发现明显不符合本规范，且修正不会扩大无关范围，应一并修正。

## 协议和客户端交互

1. 自定义协议必须固定字段顺序、字段宽度、端序、枚举值和失败语义。
2. Java 服务端与 C++ DLL 共享协议时，必须在文档和测试中同时锁定二进制布局。
3. 不使用 NPC 对话文本作为业务身份；交互身份使用类型、ID、状态和服务端权威上下文。
4. 客户端上报的对象 ID 只作为辅助信息；涉及 NPC 时，服务端必须用当前地图对象解析真实 NPC ID。
5. fallback 必须有防重入机制，避免原始点击被客户端或服务端再次 Hook。

## 资源与语言

1. 中文服自定义脚本只维护在 `scripts-zh-CN`。
2. 中文服自定义 WZ 只维护在 `wz-zh-CN` 和客户端 `Data/*`。
3. 基础 `scripts`、`wz` 保留原生内容，不承载生命之证、怪物卡戒指等中文服自定义任务逻辑。
4. 服务端和客户端语言固定为 `zh-CN`；`SwitchChinese=true` 视为历史残留，不作为可切换能力。

## 测试和验收

1. 代码改动后优先运行与改动范围匹配的聚焦测试。
2. 跨模块、协议、SQL、WZ、客户端 DLL 或服务端脚本改动必须扩大验证范围。
3. 测试命令必须确认实际命中目标；出现 `no tests to run`、空跑或跳过时不能当作通过。
4. 联调服务端必须使用 `scripts/start-wsl-server.sh`，不要操作 Windows MySQL 或临时启动流程。
5. 未能运行的测试必须在交付总结里明确说明原因和风险。

## Git 和交付

1. 提交前必须运行 `git status --short`、`git diff --name-status` 和必要的 `git diff --check`。
2. 有既有用户改动时，只提交本次任务相关文件；无法安全区分时先说明。
3. 默认不 push、不改远端历史。
4. 交付总结必须包含改动范围、行为变化、已运行验证、未验证风险和建议提交说明。
